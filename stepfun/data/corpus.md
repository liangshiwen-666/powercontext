# 示例语料：端侧 RAG 与 seekdb 技术笔记

本文件是应用内置的演示语料，按 `## 标题` 切分成多篇文档。你可以用同样的格式放自己的内容，或直接上传 .txt/.md 文件。

## seekdb 是什么

seekdb 是面向 AI 应用的嵌入式向量数据库，兼容 MySQL 协议，既可以作为库嵌进进程，也可以作为独立服务启动。它把稠密向量索引、稀疏向量索引和全文索引放在同一个引擎里，因此向量检索与关键词检索可以在一条 SQL 里完成融合排序，而不需要在应用层分别查两路再自己拼。对 RAG 场景来说，这意味着少一次网络往返，也少一份需要维护的排序逻辑。

## 混合检索与 RRF 融合

纯向量检索擅长语义相近但用词不同的情况，纯关键词检索擅长专有名词、编号、代码符号。混合检索把两路结果按名次融合：常见做法是 RRF（Reciprocal Rank Fusion），对每个文档计算 1/(k+rank) 之和，k 一般取 60。RRF 只用名次不用原始分数，因此不需要把余弦距离和 BM25 分数归一化到同一量纲，工程上更稳。seekdb 的 hybridSearch 接口在数据库内部完成这一步，应用只拿到最终排序。

## HNSW 向量索引

HNSW 是分层可导航小世界图，查询时从稀疏的上层快速逼近目标区域，再在底层精细搜索。常用参数有 M（每个节点的最大连接数）、ef_construction（建图时的候选集大小）和 ef_search（查询时的候选集大小）。M 和 ef_construction 越大，索引质量越好但构建越慢、占用内存越多；ef_search 越大，召回越高但延迟越高。对几万条文档的个人知识库，M=16、ef_construction=200 是常见的平衡点。

## 全文索引与中文分词

英文全文检索按空格切词即可，中文需要分词器。ik 分词器提供 smart 和 max_word 两种模式：smart 模式在歧义处给出粗粒度切分，召回高、索引小；max_word 模式切得更细，召回更高但可能引入噪声。全文索引的本质是倒排表，把词映射到文档列表，再按词频、文档频率和文档长度计算相关性分数。中文查询里混入英文缩写时，分词器通常会把连续字母数字当成一个词。

## 索引刷新与最终一致性

向量索引的维护有同步和异步两种模式。异步模式下写入先返回，索引在后台合并，因此刚写入的数据可能短暂检索不到，属于最终一致。对演示型应用这没问题，但用户导入完立刻搜索就会觉得"没生效"。解决办法是写入结束后显式调用一次刷新，把增量合并进索引。刷新的代价与增量大小相关，所以批量导入时应该攒够一批再刷，而不是每写一条刷一次。

## 嵌入式模式与服务器模式

嵌入式模式把数据库当成进程内的库，数据落在本地目录，没有独立端口，部署最简单，适合单机应用和比赛演示。服务器模式对外暴露 MySQL 端口，多个进程可以共享同一份数据，适合需要备份、监控或多客户端访问的场景。两种模式共用同一套客户端接口，切换时只需要改连接参数：给 path 就是嵌入式，给 host/port 就是服务器。要注意不同操作系统对嵌入式模式的支持程度不一样。

## 端侧推理与 Transformers.js

Transformers.js 把 Hugging Face 的模型推理搬进浏览器，底层是 ONNX Runtime Web。它可以在 Web Worker 里加载 ONNX 模型，做分词、前向计算和后处理，全程不联网。对 embedding 模型来说，一次前向就能得到句向量，配合池化（CLS 或 mean）和归一化，输出可直接用于余弦相似度。把推理放进 Worker 的好处是主线程不被阻塞，进度和结果通过 postMessage 传回。

## WebGPU 推理后端

WebGPU 是浏览器的新一代图形与计算接口，能直接调度 GPU 的计算着色器。对矩阵乘法密集的 Transformer 前向来说，WebGPU 通常比 WebAssembly 快数倍，尤其在批量编码时优势明显。启用方式是创建推理会话时显式指定 webgpu 执行提供者，并选用半精度权重以减少显存占用。WebGPU 并非所有设备和浏览器都可用，需要先检测 navigator.gpu 是否存在、能否成功申请到适配器。

## WASM 后端与降级策略

WebAssembly 后端是兼容性最好的选择，任何现代浏览器都能跑。它支持 SIMD 和多线程，前者能明显加速量化模型的整数运算，后者依赖跨源隔离响应头。降级策略应该是分层的：先尝试 WebGPU，失败则回退 WASM，并把降级原因显示在界面上，而不是静默切换。用户需要知道当前用的是哪个后端，否则性能数据无法解释，排查问题也无从下手。

## INT8 动态量化

动态量化在模型加载后把权重从 FP32 压到 INT8，激活值在运行时按张量动态确定缩放系数，不需要校准数据集。对 BERT 类模型，权重占体积的绝大部分，因此体积通常能压到四分之一左右，而检索质量下降往往在百分之一以内。它的代价是推理时要额外做量化与反量化，CPU 上通常更快（内存带宽省了），GPU 上则要看具体实现是否支持整数运算。

## 量化前后的体积口径

比较模型体积要统一口径：只算实际参与推理的权重文件，还是把分词器、配置文件也算进去。前者能反映显存和带宽压力，后者反映用户首次下载的流量。两种口径都合理，但必须写清楚。压缩比一般定义为量化前体积除以量化后体积，FP32 到 INT8 理论上是 4 倍，实际因为部分层保持浮点、存在少量额外元数据，通常在 3.8 到 4.0 倍之间。

## 文本切块策略

切块决定了检索的粒度：块太大，向量被无关内容稀释，命中后展示的内容也冗长；块太小，上下文不完整，模型难以判断语义。中文技术文档常用 300 到 500 字一块，块间保留 10% 到 20% 的重叠，避免把一句话拦腰截断。切块应优先在段落和句号处断开，而不是机械按字数截断。标题可以拼进块文本一起编码，能显著提升召回。

## RAG 的基本链路

检索增强生成分两步：先把用户问题编码成向量，在知识库里找出最相关的若干片段；再把这些片段作为上下文交给生成模型。第一步的质量上限决定了整个系统的上限，因为生成模型只能看到被检索出来的内容。因此工程上要重点关注切块质量、混合检索的融合策略，以及查询侧的改写。评测时通常看 Recall@K 和 nDCG@K，前者衡量有没有找全，后者衡量排序好不好。

## 查询侧与文档侧的编码差异

有些检索模型要求查询和文档用不同的前缀或指令。例如 BGE 系列建议给查询加上"为这个句子生成表示以用于检索相关文章"这类指令，而文档侧不加。这样做能让查询向量落在更适合检索的子空间里。如果两侧都用同样的方式编码，效果通常也能用，但会损失一些召回。实现时要把这个差异做成显式开关，并在技术说明里写清楚，否则复现结果会对不上。

## 增量导入与状态管理

知识库不是一次建成的。用户会不断加入新文档、删除旧文档、切换到另一个集合。因此应用需要维护三类状态：当前集合、每个集合的文档数、以及"已写入但尚未刷新索引"的计数。写入成功后计数加一，刷新成功后清零。界面要能显示这些状态，让用户知道搜索结果为什么和预期不一致。集合切换时必须清空上一次的检索结果，否则会出现"结果来自另一个库"的错觉。

## 阶跃星辰与多模态模型

阶跃星辰是一家专注多模态大模型的团队，发布了 Step 系列语言与多模态模型，覆盖文本理解、图像理解和语音等方向。在本项目中并不要求使用阶跃星辰的模型：题目允许自选可公开获取的开源 embedding 模型，关键约束是推理必须发生在用户设备上，不能调用云端推理接口。选择模型时主要看体积、中文效果和浏览器端运行的可行性。

## 性能计时的口径

报告性能要区分几个阶段：模型下载与加载（首次）、文档向量化（批量）、写入与索引刷新、查询向量化（单条）、数据库检索，以及从用户点击到结果渲染的端到端时间。首次加载包含下载和编译，通常比预热后慢一个数量级，两者必须分开报告。单次测量噪声大，应该重复多次取中位数，并保留原始数据。同一组对比实验里，除被测变量外其余条件必须保持一致。

## BM25 与稀疏向量检索

BM25 是经典的词频检索打分函数，考虑词频饱和、逆文档频率和文档长度归一化，对精确术语匹配非常有效。把它做成稀疏向量（维度等于词表大小，只有一个文档里出现的词非零）之后，就能和稠密向量放进同一个数据库统一管理。稀疏检索的短板是不知道同义词，用户说"笔记本"而文档写"便携电脑"时完全匹配不上；稠密检索正好相反，语义能对上但专有名词容易丢。这也是混合检索存在的理由。

## 余弦距离、内积与 L2

余弦距离只看方向不看长度，适合文本向量；内积会受向量长度影响，常用于经过特殊训练的模型；L2 是欧氏距离，对长度敏感。如果向量在写入前已经归一化，余弦相似度与内积等价，L2 距离也和它们单调对应。混用度量会导致排序异常，所以建索引时的度量参数必须和编码时的归一化策略一致。本项目统一做 L2 归一化，索引统一用 cosine。

## 索引重建与增量合并

向量索引有两种维护方式：写入时直接插入图中，或者先写日志再定期批量合并。前者延迟低但频繁小批量写入会让图结构变差；后者写入快但检索存在延迟窗口。生产系统通常在两者之间取平衡：小批量走增量，大批量导入完成后做一次合并。是否重建还取决于删除比例，墓碑过多时召回会下降，需要重建索引来回收。

## 元数据过滤与标量索引

除了向量相似度，检索经常需要按元数据过滤，比如只搜某个来源的文档、只看最近一周的内容。过滤可以前置（先筛出候选集再算相似度）也可以后置（先取 topK 再过滤），前者结果准确但要扫描，后者可能过滤后剩不下几条。给过滤字段建标量索引能显著改善前置过滤的性能。元数据字段不宜过多，每个字段都会增加存储与写入开销。

## 文档 ID 与重复导入

同一个文件被导入两次会产生两套向量，检索结果里出现重复内容。解决办法是给文档算一个稳定 ID，比如标题加内容的哈希；再用这个 ID 作为主键做覆盖写。块 ID 用文档 ID 加序号，保证重新导入时能定位到同一块。如果只做插入不做覆盖，就要在导入前先按 ID 删除旧数据，否则集合会越滚越大。

## 分块大小与召回率

块越小，向量越"纯"，与查询的匹配信号越强，但上下文不足；块越大，语义越完整，但无关内容会稀释向量。经验上中文技术文档 300 到 500 字比较合适。另外要注意块大小与评测口径的关系：块小的时候同一个问题可能命中同一文档的多个块，文档层面的召回看起来更好，但返回内容重复。评测时要在块级和文档级之间明确选一个。

## WebGL 与 WebGPU 的区别

WebGL 是图形 API，做通用计算要靠片元着色器绕路，缺少计算着色器和显存写回能力，跑 Transformer 很别扭。WebGPU 引入了计算管线、存储缓冲区和更灵活的内存模型，能直接表达矩阵乘法这类算子。两者的浏览器支持面不同：WebGL 几乎全覆盖，WebGPU 需要较新的浏览器和驱动。推理框架通常优先 WebGPU，不可用时退回 WebAssembly。

## 模型蒸馏与小模型

蒸馏是让小模型模仿大模型的输出分布，从而在参数量小得多的前提下保留大部分能力。常见做法是用大模型给无标注语料打分，构造软标签，再让小模型拟合。对 embedding 模型来说，蒸馏的收益体现在同维度下更强的语义区分度。它和量化是两条正交的路线：蒸馏改的是参数数量和结构，量化改的是参数的存储精度，两者可以叠加。

## LoRA 微调

LoRA 冻结原模型权重，只训练一对低秩分解矩阵，把增量叠加到指定层上。好处是显存占用小、产物只有几十 MB、可以按场景切换。但本题不要求训练模型，端侧场景下微调还会带来额外的部署复杂度：需要把适配器合并进 ONNX 图，否则推理时要多跑一次矩阵乘。对通用中文检索，现成的 BGE 系列通常已经够用。

## ONNX 模型格式

ONNX 是跨框架的模型交换格式，用计算图描述算子与张量形状。浏览器端的推理引擎读取 ONNX 图，把算子映射到 WebGPU 或 WebAssembly 实现。导出时要注意动态维度：句子的长度是变化的，batch 维度也是变化的，这些轴必须声明为动态，否则只能跑固定形状。量化工具也是在 ONNX 图上做，把权重张量替换成低精度表示并插入量化节点。

## 浏览器缓存与 Cache API

模型文件动辄几十 MB，每次刷新都重新下载不可接受。Cache API 可以把响应按 URL 存进浏览器缓存，Service Worker 或推理库在加载前先查缓存。首次加载慢、二次加载快的差异非常明显，报告性能时必须区分这两种情况。缓存有配额上限，也可能被浏览器在磁盘紧张时清理，所以要有缓存失效后的降级路径，而不是假设一定命中。

## 跨源隔离与多线程 WASM

WebAssembly 的多线程依赖 SharedArrayBuffer，而 SharedArrayBuffer 要求页面处于跨源隔离状态，也就是响应头里同时带上 COOP 和 COEP。没有这两个头，多线程回退成单线程，速度差好几倍。代价是跨源资源必须带 CORP 头或者用代理，第三方图片、字体可能加载失败。是否开启要在兼容性和性能之间权衡。

## 浏览器存储配额

浏览器给每个源分配存储配额，IndexedDB、Cache API、OPFS 共享这个额度。存模型权重、存向量缓存都要考虑配额，超出后写入会抛异常。查询配额可以用 StorageManager 接口，申请持久化存储能降低被清理的概率。把大文件放进 OPFS 比放进 IndexedDB 更合适，前者是文件语义，后者适合结构化数据。

## 离线优先与 PWA

离线优先意味着应用在断网时仍能完成核心流程。对本项目来说，模型和页面静态资源可以缓存，向量化和检索都在本地，唯一的外部依赖是本地数据库服务。加上 manifest 和 Service Worker 之后可以安装成桌面应用。注意离线能力不等于可以省掉服务端，数据库进程仍然要在本机跑着。

## 隐私与数据不出端

端侧推理的一个实际价值是隐私：文档内容和查询都不离开设备。但要真正成立，需要检查所有可能的出网点：模型下载、遥测、字体、分析脚本。任何一个第三方请求都会破坏这个承诺。可以在页面里加内容安全策略限制 connect-src，只允许本地地址，这样即使代码里误加了外部请求也会被浏览器拦下。

## 进度反馈与取消

批量导入可能持续几十秒，没有进度用户会以为卡死。进度要按阶段展示：读取、切块、向量化、写入、刷新，每个阶段的单位不同。取消功能同样重要，用户改主意时要能中断，并且中断后不留下半截数据。实现上可以在每个批次之间检查取消标记，已写入的批次要么保留并标记，要么按批次 ID 回滚。

## 错误处理与重试

网络请求和数据库写入都可能失败。失败时要区分可重试与不可重试：超时、连接中断可以重试，维度不匹配、参数非法重试也没用。重试要带退避，避免在服务刚恢复时打出请求风暴。用户可见的错误信息要说清下一步动作，比如"数据库未启动，请先运行 docker compose up"，而不是抛出原始堆栈。

## 冷启动与预热

冷启动包含进程启动、模型下载与编译、数据库连接建立，往往比稳态慢一个数量级。预热是指在正式测量前先跑几次，让编译缓存生效、连接池建立、页表热起来。报告性能时应该分开写：首次加载耗时、预热后单次耗时。只报预热后的数字会掩盖真实体验，只报冷启动又低估了系统的稳态能力。

## 评测集设计与干扰项

如果评测集里每个问题都只有一篇明显相关的文档，任何模型都能拿满分，测不出差异。好的评测集需要干扰项：主题相近但答案不同的文档，比如"HNSW 参数"和"索引刷新"都谈索引，但问题只针对其中一个。另外要有一定比例的语义型查询，不能全是关键词命中，否则纯 BM25 就能拿高分，掩盖向量检索的作用。

## 中位数、P95 与重复测量

单次测量受系统噪声影响很大，尤其是浏览器里还有垃圾回收、其他标签页抢占。规范做法是重复至少 10 次，报告中位数和 P95，并保留全部原始数据。中位数反映典型体验，P95 反映长尾卡顿。只报最快一次是误导，只报平均会被个别异常值拉偏。如果两次实验差异小于噪声范围，就不能声称优化有效。

## 端到端延迟的组成

用户感知的延迟从点击检索开始，到结果渲染完成结束，包含查询编码、网络往返、数据库检索和前端渲染四段。优化时要先测量各段占比，再决定投入方向。如果编码占了九成，优化数据库索引收益很小；反之如果数据库是瓶颈，换更大的模型只会更慢。分段计时还能暴露隐藏开销，比如首次请求时的连接建立。

## 向量归一化与相似度一致性

编码时做归一化，检索时才算余弦相似度，这是最常见的不一致来源。如果写入的向量没有归一化而查询向量归一化了，点积分数会偏向长文档。统一的做法是在编码端归一化，数据库端用 cosine 度量，两端都不要再做额外缩放。量化会让归一化后的向量产生微小偏移，通常不影响排序，但在阈值判定场景要留余量。

## RRF 的 k 参数

RRF 的分母是 k 加上名次，k 越大，名次之间的分数差距越小，融合越平滑；k 越小，头部结果的话语权越集中。常用值是 60，来自最初的论文实验。k 的选择会影响混合检索的偏向：k 小时更像"取两路交集"，k 大时更像"取两路并集"。如果发现某一路结果总是主导排序，可以调整 k 或者给两路不同的权重。
